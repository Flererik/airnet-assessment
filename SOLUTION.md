# Решение

## Затраченное время

- Настройка окружения: ~10 минут. Docker Hub в моём окружении был недоступен
  (`docker compose up` → `Forbidden` при загрузке образов), поэтому запуск
  выполнен по `docs/local.md`: PostgreSQL 16 локально, PHP **7.4.33** собран
  из исходников (`--with-pgsql --enable-session --enable-json`), Vite dev-сервер.
  Решение проверялось именно на PHP 7.4, а не на 8.x.
- Разработка (воспроизведение, исправления, тесты, документация): ~40 минут
  с ИИ-агентом + время на собственный разбор и ревью diff.

## Найденные причины

### 1. При быстром переключении открываются данные предыдущей заявки

- **Воспроизведение.** С `DEMO_LATENCY=1` карточка 101 отвечает ~1.1 с, остальные ~0.1 с.
  Клик по #101, сразу по #102 → через секунду в карточке «Не работает интернет» (101).
  Автотест: `поздний ответ предыдущей заявки не подменяет выбранную` в
  `frontend/src/App.test.jsx` — падает на исходном коде.
- **Причина.** `TicketPanel` в `useEffect` запускал `api('/tickets/:id')` без отмены
  и без проверки, что ответ относится к текущему `selectedId`. Ответ, пришедший
  последним, выигрывал. Та же проблема была у `save()`: ответ сохранения заявки A
  после перехода на B записывался в карточку B (`setTicket(data.ticket)`), а ошибка
  сохранения A показывалась в карточке B.
- **Исправление** (`TicketPanel.jsx`):
  - каждая загрузка получает номер (`loadSeqRef`); ответ применяется, только если
    его номер всё ещё последний; при смене заявки запрос отменяется `AbortController`;
  - при смене заявки старые данные сразу сбрасываются (видна «Загрузка карточки…»,
    а не прошлая карточка);
  - ответ/ошибка сохранения применяются к карточке, только если выбрана та же заявка
    (`selectedRef`); список обновляется всегда — изменение на сервере уже произошло;
  - успешное сохранение «перебивает» незавершённую загрузку той же заявки
    (сценарий A → B → A во время сохранения), чтобы старые данные не затёрли новые;
  - повторная отправка блокируется синхронно через `savingRef` (а не только
    `disabled` и state, который обновляется асинхронно).
- **Проверка.** 11 тестов Vitest + Testing Library с фейковым `fetch`, где тест сам
  решает порядок ответов (детерминированно, не зависит от задержек). 4 теста о
  гонках падают на исходном коде и проходят после исправления. Дополнительно
  вручную прогнал сценарий в Chromium (Playwright) на живом стеке
  с `DEMO_LATENCY=1` и `DEMO_LATENCY=0`.

### 2. Карточка заявки без источника загружается с ошибкой

- **Воспроизведение.** `GET /api/tickets/103` → `500 internal_error`.
  Автотест `test_ticket_without_source`.
- **Причина.** `TicketRepository::find()` отдельным запросом искал источник по
  `source_id = NULL`, получал `false` и обращался к `$source['id']`. В PHP 7.4 это
  notice «Trying to access array offset on value of type bool», который
  `set_error_handler` превращает в исключение → 500.
- **Исправление.** Один запрос с `LEFT JOIN sources`; при отсутствии источника
  `source: null`. UI показывает «Не указан» (в т.ч. в выпадающем списке редактора).
- **Проверка.** API: `source === null`, `source_name === null` в списке, установка
  источника для 103 пишет историю с `old_source_id: null`. UI-тест на «Не указан».

### 3. Сотрудник с правом только на просмотр смог изменить источник

- **Воспроизведение.** Вход `viewer`, `POST /api/tickets/102/source {"source_id":3}` →
  `200`, источник изменён, в истории «Анна Примерова». Так же меняется архивная 104.
  Автотест `test_viewer_cannot_change_source` (+ подделка полей
  `employee_id`/`permissions` в теле).
- **Причина.** Маршрут проверял только общее `FUNC_TICKETS_VIEW`; права
  `FUNC_TICKETS_SOURCE_EDIT` проверялись лишь в React (`canEdit` скрывал селект).
  Проверки архива на сервере не было вовсе.
- **Исправление.** В маршруте сразу после CSRF — `requirePermission($employee,
  'FUNC_TICKETS_SOURCE_EDIT')`, где `$employee` и права берутся из БД по
  серверной сессии. Тело запроса читается только после этого, кроме `source_id`
  из него ничего не используется.

### Доведение смены источника до требований

`TicketRepository::changeSource()` выполняется в одной транзакции:

1. `SELECT status, source_id … FOR UPDATE` — нет заявки → **404**;
2. `status = 'archived'` → **403**;
3. `source_id` не JSON-integer в диапазоне `1..2147483647` или нет в `sources` → **400**
   (строки, дроби в т.ч. `2.0`, `null`, `true`, массивы, отсутствующее поле,
   невалидный JSON, неизвестный и выходящий за `integer` id);
4. если источник не меняется → `COMMIT`, **200** без записи истории;
5. иначе `UPDATE tickets` + `INSERT ticket_history` (сотрудник из сессии,
   `created_at` = `clock_timestamp()` БД) → `COMMIT`, **200** с карточкой и историей,
   прочитанными в той же транзакции.

Любое исключение → `ROLLBACK` и проброс. Ошибки бизнес-логики — `HttpError`,
глобальный обработчик превращает их в JSON с нужным статусом; прочие исключения —
500 `{"error":"internal_error","message":"Не удалось обработать запрос"}`,
детали только в `error_log`.

Порядок для запроса: нет сессии **401** → CSRF **403** → нет права **403**
(до чтения тела и до каких-либо обращений к заявке) → далее шаги 1–5.
Слишком большой id заявки в пути (`/api/tickets/99999999999`) теперь даёт 404,
а не 500 от PostgreSQL (`integer out of range`).

## Решения и компромиссы

- **Исключение `HttpError` вместо `respond()+exit` внутри репозитория.** Раньше
  `respond()` вызывался изнутри репозитория и завершал скрипт; внутри транзакции
  это оставило бы её открытой до закрытия соединения. С исключением откат явный.
- **Невалидный `source_id` передаётся в репозиторий как `null`**, а не отклоняется
  в маршруте сразу: требование задаёт порядок «заявка → архив → источник», поэтому
  для несуществующей заявки с мусором в теле правильный ответ 404, для архивной — 403.
- **`FOR UPDATE`** — минимальная защита целостности истории при параллельных
  запросах (без неё два запроса читали один и тот же старый `source_id`, и в
  истории появлялись «разорванные» цепочки — тест
  `test_concurrent_changes_keep_consistent_history` ловит это на исходном коде).
- **Фронтенд:** счётчик загрузок + `AbortController`, а не только флаг `active` в
  cleanup — счётчик позволяет ответу сохранения «закрыть» более старую загрузку той
  же заявки. Сторонних библиотек (React Query и т.п.) не добавлял — требование
  не менять стек.
- Одно сохранение за раз на панель: во время сохранения кнопка «Сохранить»
  недоступна, даже если пользователь уже перешёл на другую заявку. Проще и
  безопаснее, чем отслеживать несколько параллельных сохранений.
- Список после сохранения обновляется из ответа сервера (`source_name` строки),
  без перезапроса `/tickets` — ответ уже содержит актуальную карточку.
- В `api.js` не-JSON ответ (например, 502 от прокси) больше не приводит к
  `SyntaxError` в интерфейсе — показывается «Ошибка сервера (HTTP …)».

## Запуск проверок

Приложение должно быть запущено (`docker compose up --build` или по `docs/local.md`).
API-тесты сбрасывают учебную БД через `database/reset.sql`.

```sh
# API (Python 3, только stdlib). Локальный psql с переменными PG*:
python3 tests/api_test.py http://localhost:5173

# То же при запуске через Docker Compose:
RESET_DB_CMD="docker compose exec -T db psql -U assessment -d airnet_assessment" \
  python3 tests/api_test.py http://localhost:5173

# Фронтенд (Vitest + Testing Library, jsdom; сервер не нужен):
cd frontend && npm test
# или в контейнере: docker compose exec frontend npm test

# Готовая smoke-проверка:
python3 tools/smoke.py http://localhost:5173
```

Фактические результаты (PHP 7.4.33, PostgreSQL 16, Node 22):

| Проверка | Исходный код | После исправления |
|---|---|---|
| `tests/api_test.py`, `DEMO_LATENCY=1` | 10 из 16 падают | 16/16 OK |
| `tests/api_test.py`, `DEMO_LATENCY=0` | — | 16/16 OK |
| `npm test` | 4 из 11 падают (гонки загрузки/сохранения) | 11/11 OK |
| `tools/smoke.py` | PASS | PASS |
| `npm run build` | OK | OK |
| `php -l` (7.4) всех файлов backend | — | OK |

Исходную ошибку воспроизводят, например: `test_viewer_cannot_change_source`,
`test_ticket_without_source`, `test_concurrent_changes_keep_consistent_history`,
`test_history_failure_rolls_back_change` (API) и
«поздний ответ предыдущей заявки не подменяет выбранную» (React).

Тест атомарности временно создаёт на `ticket_history` триггер, падающий на INSERT,
и проверяет: ответ 500 без внутренних деталей, источник не изменился, следующая
операция проходит. Триггер удаляется в `finally`.

## Одновременное редактирование

Два редактора открыли заявку 101 (источник «Телефон»). Первый сохраняет «Личный
кабинет», второй — «Сотрудник».

- Запросы сериализуются блокировкой строки (`FOR UPDATE`), поэтому данные и история
  остаются согласованными: история будет `Телефон → Личный кабинет` (первый),
  `Личный кабинет → Сотрудник` (второй). «Разорванной» истории или потерянной
  записи истории не будет.
- Но действует правило «последний выигрывает»: второй сотрудник выбирал, видя
  «Телефон», и не узнает, что перезаписал чужое изменение (в ответе он увидит
  историю из двух записей). Карточка первого сотрудника продолжит показывать
  «Личный кабинет», пока он не переоткроет заявку.
- Если оба выбрали один и тот же источник, второй получит успех без новой записи.

Чтобы предотвращать потерю изменений, можно передавать с клиента ожидаемый
`source_id` (или `updated_at`) и при расхождении с текущим значением под
`FOR UPDATE` возвращать `409 Conflict` с актуальной карточкой.

## Оставшиеся ограничения

- Docker-запуск в моём окружении не проверен (недоступен Docker Hub); проверено
  по `docs/local.md` на тех же версиях PHP/PostgreSQL. Node 22 вместо 24 для
  тестов/сборки — Vite и Vitest работают, `engines` не менял.
- Нет E2E-теста в настоящем браузере в составе репозитория (сценарий проверен
  вручную Playwright-скриптом, не коммитил, чтобы не добавлять браузерные
  зависимости). React-тесты покрывают те же гонки детерминированно.
- Защита от конфликтов (409) не реализована — см. выше.
- Во время сохранения нельзя сохранить другую заявку (кнопка недоступна до ответа).
- Тест параллельности вероятностный по природе: на исходном коде он стабильно
  падал у меня, но может не воспроизвести гонку на очень медленной машине;
  на исправленном коде ложных падений быть не должно.
