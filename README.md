# Учебный модуль заявок: PHP + React — решение

История в Git:

1. `Исходное состояние проекта` — архив задания без изменений.
2. Второй коммит — исправления, тесты и документация. Весь diff решения: `git show HEAD`.

## Что было не так и что я сделал

### 1. При быстром переключении открывались данные предыдущей заявки

**Почему.** Карточка (`TicketPanel.jsx`) загружала заявку в `useEffect`, но не
отменяла старый запрос и не проверяла, к какой заявке относится ответ. С учебной
задержкой заявка 101 отвечает ~1.1 с, остальные ~0.1 с: если кликнуть 101, а затем
102, ответ 101 приходит последним и перезаписывает карточку. Та же ошибка была
у сохранения: ответ (или ошибка) сохранения заявки A после перехода на B
подставлялся в карточку B.

**Как исправил.**
- Каждая загрузка получает порядковый номер; ответ применяется, только если он
  всё ещё последний. При смене заявки старый запрос отменяется через `AbortController`.
- При переключении старая карточка сразу скрывается и показывается «Загрузка…».
- Ответ сохранения применяется к карточке, только если выбрана та же заявка.
  Строка в списке обновляется в любом случае — изменение на сервере уже произошло.
- Если во время сохранения пользователь ушёл на другую заявку и вернулся,
  устаревшая загрузка не затирает результат сохранения.
- Повторная отправка блокируется синхронно через `useRef`, а не только через
  `disabled` (state обновляется асинхронно, и быстрый двойной клик мог проскочить).

Задержки API я не трогал — решение работает и с ними, и без них.

### 2. Карточка без источника загружалась с ошибкой

**Почему.** `TicketRepository::find()` отдельным запросом искал источник по
`source_id = NULL`, получал `false` и читал `$source['id']`. В PHP 7.4 это notice,
который обработчик ошибок превращает в исключение → ответ 500.

**Как исправил.** Один запрос с `LEFT JOIN sources`; если источника нет —
`"source": null` в JSON. Интерфейс показывает «Не указан» и в карточке, и в списке,
и в выпадающем списке редактора.

### 3. Сотрудник с правом только на просмотр смог изменить источник

**Почему.** Маршрут смены источника проверял только общее право
`FUNC_TICKETS_VIEW`. Право `FUNC_TICKETS_SOURCE_EDIT` проверялось лишь в React
(кнопка скрывалась), поэтому прямой POST от просмотрщика проходил. Запрета на
изменение архивных заявок на сервере не было совсем.

**Как исправил.** Сразу после CSRF-проверки сервер требует
`FUNC_TICKETS_SOURCE_EDIT`. Сотрудник и его права берутся из БД по серверной
сессии; из тела запроса используется только `source_id`, поля вроде
`employee_id` или `permissions` игнорируются. Отказ происходит до чтения тела
и до любых обращений к заявке.

### Смена источника по требованиям

Логика в `TicketRepository::changeSource()`, всё в одной транзакции:

| Шаг | Условие | Ответ |
|---|---|---|
| 1 | `SELECT … FOR UPDATE` — заявки нет | 404 |
| 2 | заявка архивная | 403 |
| 3 | `source_id` не целое число 1…2147483647 или нет в `sources` | 400 |
| 4 | источник не меняется | 200, без записи в историю |
| 5 | `UPDATE tickets` + `INSERT ticket_history` → `COMMIT` | 200, карточка и история |

До этих шагов: нет сессии — 401, неверный CSRF или нет права — 403.

Решения, которые я принимал по ходу:

- **Порядок проверок.** В исходном коде `source_id` валидировался до поиска заявки.
  По требованию для редактора порядок другой: заявка → архив → источник. Поэтому
  маршрут не отклоняет некорректный ввод сразу, а передаёт его как `null`,
  и 400 возвращается только после проверок 404 и 403.
- **Строгая проверка типа.** Принимается только JSON-integer: строка `"2"`,
  дроби (включая `2.0`), `null`, `true`, массивы, отсутствующее поле, невалидный
  JSON и числа за пределами PostgreSQL `integer` дают 400, а не 500.
- **Транзакция и откат.** Ошибки бизнес-логики выбрасываются как `HttpError`, а не
  через `respond()+exit` внутри репозитория, чтобы транзакция гарантированно
  откатывалась. Любая непредвиденная ошибка — 500 с общим сообщением, детали
  только в журнале сервера.
- **`FOR UPDATE`.** Без блокировки два параллельных запроса читали одно и то же
  старое значение, и в истории появлялись несогласованные записи. Блокировка
  строки заявки сериализует изменения.
- **Мелочь.** Слишком большой id заявки в URL (`/api/tickets/99999999999`)
  раньше давал 500 из-за переполнения `integer` в PostgreSQL, теперь — 404.
  А `api.js` теперь показывает понятную ошибку, если сервер вернул не JSON.

### Одновременное редактирование

Защиту от потери изменений по заданию делать не требовалось. В текущей
реализации изменения сериализуются: если двое меняют одну заявку, история будет
последовательной (`Телефон → Личный кабинет`, затем `Личный кабинет → Сотрудник`),
но действует правило «последний выигрывает». Второй сотрудник не узнает, что
перезаписал чужое изменение. Следующим шагом я бы передавал с клиента ожидаемый
текущий источник и возвращал `409 Conflict` при расхождении.

## Запуск

Нужен Docker с Compose v2. Из корня проекта:

```sh
docker compose up --build
```

Откройте http://localhost:5173, выберите роль и нажмите «Войти»
(«Просмотр» — Анна Примерова, «Редактор» — Илья Учебный).
Запуск без Docker описан в [docs/local.md](docs/local.md).

Сброс данных:

```sh
docker compose exec -T db psql -U assessment -d airnet_assessment < database/reset.sql
```

## Проверки

Тесты проверяют поведение через HTTP и интерфейс, а не наличие строк в коде.

```sh
# Готовая smoke-проверка
python3 tools/smoke.py http://localhost:5173

# API-тесты (только стандартная библиотека Python; сбрасывают учебную БД)
RESET_DB_CMD="docker compose exec -T db psql -U assessment -d airnet_assessment" \
  python3 tests/api_test.py http://localhost:5173

# Тесты интерфейса
docker compose exec frontend npm test
```

Без Docker вместо `RESET_DB_CMD` достаточно переменных `PG*` из `docs/local.md`,
фронтенд-тесты — `cd frontend && npm test`.

Что покрыто:

- **API:** 401 без сессии; 403 для просмотрщика, в том числе с подделанными
  полями в теле; просмотрщик видит список, карточку и историю; карточка без
  источника; успешное изменение с сотрудником из сессии; повтор без новой записи;
  14 вариантов некорректного `source_id` и невалидный JSON; порядок 404 → 403 → 400;
  CSRF; атомарность (сбой записи истории откатывает изменение, 500 без деталей);
  параллельные изменения дают согласованную историю.
- **React:** поздний ответ загрузки и ответ или ошибка сохранения предыдущей
  заявки не подменяют карточку; повторная отправка невозможна; ошибки загрузки
  и сохранения показываются; после сохранения обновляются карточка, история
  и список; «Не указан»; режим только для чтения.

Чтобы убедиться, что тесты действительно ловят исходные ошибки, я прогонял их на
коде из первого коммита: падают 10 из 16 API-тестов и 4 из 11 тестов интерфейса.
После исправления проходят все. API-тесты проходят и с `DEMO_LATENCY=1`,
и с `DEMO_LATENCY=0`.
